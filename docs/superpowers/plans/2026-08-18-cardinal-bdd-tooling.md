# Cardinal BDD Tooling Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Wire `playwright-bdd` into the monorepo so `.feature` Gherkin files are both documentation and real executable tests, and prove the pipeline end to end against `apps/demo`.

**Architecture:** `@playwright/test` + `playwright-bdd` as root devDependencies. `playwright.config.ts` at repo root uses `defineBddConfig` to compile `features/**/*.feature` + `features/**/*.steps.ts` into runnable Playwright tests, driven by `apps/demo`'s plain-Vite dev server (`dev:runtime`, port 8081) as Playwright's own `webServer` — deliberately **not** the CLI-managed `iwsdk dev up` flow that `xr-visual-qa`'s interactive browser session uses; those are two separate execution paths (automated headless Playwright vs. an interactive managed browser) and must not be conflated. The `webServer` command runs `pnpm build` first: the demo imports compiled workspace packages, which is exactly why the repo's own `demo` script is `pnpm build && ... dev` — `vite` alone on a fresh clone fails confusingly.

**Tech Stack:** `@playwright/test`, `playwright-bdd`, TypeScript, pnpm workspace root.

**Spec:** `docs/superpowers/specs/2026-08-18-cardinal-studio-agent-team-design.md` (§3 — BDD tooling)

## Global Constraints

- Root-level devDependencies only (spec §3) — not scoped into `apps/demo`'s own `package.json`.
- Install via `pnpm add -Dw <pkg>` so pnpm resolves and pins the current version — never hand-write a guessed version number into `package.json`.
- `pnpm@10.33.0`, Node `>=20.19.0` (repo `engines`) — no tooling choice below requires more.
- One commit per task, message format `feat(bdd): <summary>` or `chore(bdd): <summary>`, trailer `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`.

### Task 2: Configure playwright-bdd and prove the red→green cycle

**Files:**
- Create: `playwright.config.ts`
- Create: `features/tooling/smoke.feature`
- Create: `features/tooling/smoke.steps.ts`
- Modify: `.gitignore`

**Interfaces:**
- Consumes: Task 1's installed packages.
- Produces: a working `playwright.config.ts` that `product-owner-bdd`'s future `.feature` files and `xr-visual-qa`'s test runs both rely on; the `features/` directory layout (`features/<area>/<name>.feature` + `.steps.ts` alongside).

- [ ] **Step 1: Write `playwright.config.ts`**

```typescript
import { defineConfig, devices } from '@playwright/test';
import { defineBddConfig } from 'playwright-bdd';

const testDir = defineBddConfig({
  features: 'features/**/*.feature',
  steps: 'features/**/*.steps.ts',
});

export default defineConfig({
  testDir,
  reporter: 'list',
  use: {
    // The IWSDK dev plugin serves HTTPS-only on 8081 (WebXR requires a
    // secure context) with a self-signed cert — hence https + ignore.
    baseURL: 'https://localhost:8081',
    ignoreHTTPSErrors: true,
  },
  webServer: {
    // Build first: the demo imports compiled workspace packages — same
    // reason the repo's `demo` script is `pnpm build && ... dev`.
    command: 'pnpm build && pnpm --filter @iwsdk/plugin-phoenix-demo dev:runtime',
    url: 'https://localhost:8081',
    ignoreHTTPSErrors: true,
    reuseExistingServer: !process.env.CI,
    timeout: 300_000,
  },
  projects: [{ name: 'chromium', use: { ...devices['Desktop Chrome'] } }],
});
```

- [ ] **Step 2: Write the smoke feature (no steps yet)**

Create `features/tooling/smoke.feature`:

```gherkin
Feature: BDD toolchain smoke test

  Scenario: The toolchain runs a scenario against a real page
    Given the demo app is running
    When I open the home page
    Then the page title is not empty
```

- [ ] **Step 3: Run it and verify it fails — no step definitions exist yet**

```bash
pnpm exec bddgen && pnpm exec playwright test
```
Expected: FAIL. `bddgen` (or the subsequent `playwright test` run) reports
undefined/missing step implementations for the three Gherkin steps —
this is deliberate; it proves the toolchain is actually parsing and
running the `.feature` file, not silently skipping it.

- [ ] **Step 4: Write the step definitions**

Create `features/tooling/smoke.steps.ts`:

```typescript
import { expect } from '@playwright/test';
import { createBdd } from 'playwright-bdd';

const { Given, When, Then } = createBdd();

Given('the demo app is running', async () => {
  // No-op: Playwright's `webServer` config already started and health-checked it.
});

When('I open the home page', async ({ page }) => {
  await page.goto('/');
});

Then('the page title is not empty', async ({ page }) => {
  await expect(page).toHaveTitle(/.+/);
});
```

- [ ] **Step 5: Run it again and verify it passes**

```bash
pnpm exec bddgen && pnpm exec playwright test
```
Expected: PASS — 1 scenario, 3 steps, all green.

### Task 4: Document the convention for story authors

**Files:**
- Create: `features/README.md`

**Interfaces:**
- Consumes: Tasks 1-3.
- Produces: the reference `product-owner-bdd` and engineers point to when adding new `.feature` files.

- [ ] **Step 1: Write the doc**

Create `features/README.md`:

```markdown
# Gherkin scenarios

One directory per feature area, `.feature` and its `.steps.ts` side by
side:

```
features/
  tooling/
    smoke.feature
    smoke.steps.ts
  <area>/
    <story-slug>.feature
    <story-slug>.steps.ts
```

- `product-owner-bdd` writes the `.feature` file (story comment at the
  top, `Étant donné/Quand/Alors` or `Given/When/Then` scenarios below).
- The engineer implementing the story, or `xr-visual-qa` for
  verification-only steps, writes the matching `.steps.ts`.
- Steps come in two kinds — do not conflate them. **DOM steps** (page
  loads, titles, the desktop HUD overlays) are plain Playwright.
  **In-scene steps** (an NPC interaction, a grab, a trade — anything
  inside the 3D scene) go through IWSDK's agent command bridge
  (simulated controller/ray input, ECS assertions — see `iwsdk-debug`
  and `iwsdk-ray`), never `page.click()` on the canvas: the canvas is a
  single opaque element to Playwright.
- Multiplayer scenarios use multiple Playwright browser contexts in one
  test — two players are two `browser.newContext()` pages against the
  same server, the automated equivalent of the demo README's "open the
  page in two tabs". Ownership races, reconciliation, and spawn/despawn
  scenarios need at least two; never write them assuming a single
  client.
- Run everything: `pnpm test:bdd`. Run one file:
  `pnpm exec playwright test features/<area>/<story-slug>.feature`.
- New scenarios drive Playwright against `apps/demo`'s plain-Vite dev
  server (`dev:runtime`, port 8081) via `playwright.config.ts`'s
  `webServer`, which runs `pnpm build` first (the demo imports compiled
  workspace packages) — this is separate from the CLI-managed
  `iwsdk dev up` flow used for interactive agent-driven browser
  verification.
```

- [ ] **Step 2: Verify the file renders as valid markdown**

Run: `head -5 features/README.md`
Expected: `# Gherkin scenarios` as the first line.

- [ ] **Step 3: Commit**

```bash
git add features/README.md
git commit -m "docs(bdd): document the features/ convention

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>"
```
